owner, admin.

## 4. owner-workspace
- [x] Dashboard and listing list (`/owner`, `/api/hostels/mine`): status filters, review-state notes, pagination, public link for live listings only, owner-only. Create/edit links are deliberately absent until those routes exist
- [x] Listing create with room editor (`/owner/listings/new`, `POST /api/hostels`). The API requires at least one room type, so the room editor ships with create. Hostel price, room count and bed count are derived from the room entries. Amenities are saved as ids (`wifi`, `cctv`) like the seed data. Room photos, map coordinates and per-room images are not in the form yet
- [x] Listing edit (`/owner/listings/[id]/edit`, `PATCH /api/hostels/[param]`): the listing is loaded server-side scoped by `ownerId` (`src/lib/owner-listing.ts`), the form prefills from it and keeps room ids, room photos and map coordinates so an edit doesn't wipe them. Any edit sends the listing back to review (the API sets `PENDING_REVIEW` and, for live listings, removes it from search), and the form says so. Unpublish (live to draft) and submit (draft to review) are separate status actions. Suspended listings show a notice instead of the form. 409 room-conflict messages come straight from the API. "Edit" is linked from the dashboard for every non-suspended listing
- [x] Booking queue with confirm/decline (`/owner/bookings`, the target of the owner booking emails): lists paid bookings from `GET /api/bookings` (the API only returns paid ones to owners), defaults to "Needs response" with status filters and pagination, shows the 24-hour response countdown, confirms in one click and declines after an explicit full-refund confirmation (`PATCH /api/bookings/[id]`). Actions disappear once the window ends; a 409 refreshes the list. Linked from the dashboard. There is no owner booking detail page, so the queue shows the student's contact details inline
- [x] Earnings (`/owner/earnings`, `GET`/`PATCH /api/owner/earnings`): "Ready for payout" balance (confirmed, paid stays past check-out and not yet in a batch), bank details card (the full account number is never shown or prefilled; only the last four digits, and changing it means re-entering the number), payout history with pagination. Linked from the dashboard. Payout batches are created by admins and the transfer happens outside the product, so the page says so rather than offering a withdraw button
- [x] Subscription (`/owner/subscription`, `GET`/`POST /api/owner/subscription`): current plan, listing usage against the Free limit, Free vs Pro comparison from `src/config/plans.ts`, and "Upgrade to Pro" which starts the Safepay checkout (only https checkout URLs are followed). Handles the `?upgraded=1` return before the webhook has activated Pro ("waiting for confirmation" with a re-check) and `?cancelled=1`. There is no cancel or downgrade API, so the page offers neither. Owner-only; linked from the dashboard
- [x] Blocked dates (`/owner/listings/[id]/blocked-dates`, `GET`/`POST`/`DELETE /api/owner/hostels/[id]/blocked-dates`): the listing is loaded owner-scoped server-side (`getOwnerListingSummary` in `src/lib/owner-listing.ts`), the form adds an inclusive date range with an optional reason (sent as `YYYY-MM-DD`; ranges are shown in UTC so days don't shift), the list is paginated and each range can be removed. The page says that blocking stops new move-in dates but doesn't cancel existing bookings, because the API doesn't check for overlapping bookings. Linked as "Blocked dates" from every non-suspended listing on the dashboard
- [x] Review replies (`/owner/reviews`, `GET /api/reviews/mine`, `PATCH`/`DELETE /api/reviews/[id]/reply`): stats (review count, average rating, reply rate), filters (All, Needs reply, Replied, Low rated), paginated review cards with the stay dates, and inline reply, edit and delete (10 to 1000 characters, same as the API). "Low rated" is the API's `flagged` filter, which is only rating 2 or lower; there is no real flagging mechanism. The page tells owners replies are public. Owner-only (the APIs also allow admins, but replies are written in the owner's voice). Linked from the dashboard

## 5. admin-console
- [x] Overview and listing review (`/admin`, `/admin/listings`; `GET /api/admin/listings/stats`, `GET /api/admin/listings`, `PATCH /api/admin/hostels`, and the admin-only `GET /api/hostels/[param]` for review details): the overview shows total, pending, incomplete (pending listings under the completeness threshold) and newly live counts. Listing review has Pending review, Live and Suspended tabs, search, pagination and an expandable details panel (address, rooms, owner history, photos, description, amenities, rules). Moderation actions: "Verify and publish" requires all four verification checks (the API's only route from pending to live, so there is no approve-without-badge), "Suspend" takes an optional reason that is sent to the owner, and "Reactivate" confirms first. A 409 (someone else changed it) refreshes the queue. Admin-only: other roles get a 404. The account menu gets an "Admin console" link for admins. The overview links only to sections that exist. Completeness is a computed content score, not a trust score. `SYSTEM.md` facts refreshed with `node scripts/check-docs.mjs --write`
- [x] Verification queue (`/admin/verifications`; `GET`/`PUT /api/admin/verifications`, `GET /api/admin/verifications/[userId]/document`): Pending, Approved and Rejected tabs (oldest submission first), search by name or email, pagination, and a confirm step before each decision. The document loads only when a reviewer opens a card, because the document route is limited to 30 requests a minute; images preview inline from the auth-checked admin route and PDFs download instead. Approve is disabled when a request has no document to look at (Reject stays available so the student can resubmit). Approved and Rejected are read-only: the API deletes the document on every decision, so there is nothing left to review. The API accepts a rejection `reason` but neither stores nor sends it, and the student notification is generic, so the page collects no reason rather than imply feedback is delivered. A 409 (another admin decided first) refreshes the queue. Admin-only: other roles get a 404. Linked from the admin overview. The verification analytics endpoint has no screen yet
- [x] Roommate reports (`/admin/roommate-reports`; `GET /api/admin/roommate-reports`, `DELETE /api/admin/roommate-reports/[postId]`): reported posts newest first with pagination, each showing the author, hostel (linked to its public page), budget, move-in, the post text and the reports with reason, reporter and date. Each post says whether it is still visible or hidden from students (hidden at the API's `hideThreshold`, currently 3 reports), and flags expired posts using the time the list was loaded so rendering stays pure. The API returns only the latest 50 reports per post, so the card says "Showing the latest N of M" when the total is larger. Delete is the only action and has a confirm step that says it is permanent and that the author is not notified (the route sends no notification). There is no dismiss-report API, so a post that was reported unfairly cannot be cleared; the page says so instead of offering a button that does not exist. The list has no filters or search and no `hasMore`, which is derived from page size and total. A 404 (another admin already deleted it) refreshes the list. Admin-only: other roles get a 404. Linked from the admin overview
- [x] Owner payouts (`/admin/payouts`; `GET`/`POST /api/admin/payouts`, `PATCH /api/admin/payouts/[id]`): owners with a ready balance or past payouts, ordered by name with pagination. "Generate payout batch" is disabled, with the reason shown, when bank details are incomplete or nothing is ready (the API enforces both). A pending batch shows the decrypted destination (title, account number, bank) so the admin can make the transfer; if the snapshot is missing or can't be decrypted the card says so and points to voiding. "Mark as paid" requires the transfer reference (max 200 characters) and warns it can't be undone. "Void batch" requires a reason (10 to 500 characters) and a checkbox confirming no transfer was sent, and says the bookings return to the owner's balance. Paid and voided batches are read-only history with reference, reason, dates and audit events. A 404 or 409 refreshes the list. The API allows more than one pending batch per owner, so the page doesn't invent a limit. Per-owner history is capped by the API (`payoutHistoryPerOwner`), and the card says when it is truncated. HostelLo doesn't move money, and the page says so. Admin-only: other roles get a 404. Linked from the admin overview
- [x] Refunds (`/admin/refunds`; `GET /api/bookings?status=CANCELLED` as admin, `PATCH /api/admin/bookings/[id]/refund`): there is no refund queue endpoint, so the page loads cancelled bookings newest first (50 per page) and shows only the paid or partly refunded ones with money left (approved amount from the cancellation terms, capped at the total, minus what was already refunded; the same arithmetic as `src/lib/refunds.ts`). Because filtering is client-side, an empty first page with more to load says "none in the bookings loaded so far" and offers "Load older bookings" instead of claiming nothing is owed. "Refund via Safepay" confirms first (irreversible; the student is notified). If Safepay doesn't confirm, the API returns success with `automatic: false` and the booking becomes unconfirmed, so the page shows that as a warning, not a success, and blocks a second automatic request. Unconfirmed and in-progress bookings offer only "Confirm refund manually", which needs a "verified in Safepay" checkbox; the API rejects manual confirmation of an in-progress refund until it has been stuck for 5 minutes, and that message is shown as is. The 5-per-hour admin refund limit is stated on the page. A 404 or 409 refreshes the list. The transaction id is never displayed. Admin-only: other roles get a 404. Linked from the admin overview. The plan previously said `POST` for the refund route; it is `PATCH`
- [x] Payment events (`/admin/payment-events`; `GET /api/admin/payment-events`, `POST /api/admin/payment-events/[id]/retry`): events in `RETRYABLE` or `RECONCILIATION_REQUIRED` state, newest first, 25 per page with "Load more" (the API sends no `hasMore`, so it is derived from page size and total). Each card shows event type, status, amount (stored in minor units, shown as PKR), order, Safepay tracker, provider state, received time, processing attempts, the last error code with a plain-language note, and up to 3 recent retries with their reasons. Retry mirrors the API's preconditions: only `RETRYABLE` events with a tracker and valid stored evidence get the action; reconciliation events and `invalid_stored_event` explain why there is no button, so nothing is offered that the API would reject. The retry form needs the exact stored tracker, a reason of 20 to 500 characters and a "checked in Safepay" checkbox, and says the attestation is recorded and cannot be edited. A 202 shows "Retry queued"; a 404 or 409 refreshes the list; the 503 messages (QStash not configured, enqueue failed) are shown as is. The 5-per-hour retry limit is stated on the page. Replays record the admin id only, so the page doesn't show who retried. Admin-only: other roles get a 404. Linked from the admin overview
- [x] Search index (`/admin/search-sync`; `POST /api/admin/search/sync`): "Sync all listings" (2 per hour, confirm step, re-indexes live listings only) and a one-listing card with "Sync this listing" and "Remove from search" (60 per hour each; removal confirms first and says the listing itself is unchanged). The route returns only a message, so the page shows that message and cannot report counts or index state. The API also reports success when no hostel has the given ID, and the page says so. The hostel ID is typed in because no admin screen shows it yet. A 429 shows the wait from `Retry-After`. Admin-only: other roles get a 404. Linked from the admin overview
